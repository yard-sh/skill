# Landing pages

A project's landing page at `https://<team>.yard.sh/<slug>/` is optional: it is the service the release mounts at `/`, usually a static one (its files and no server code), and a project without one shows a Not Found page there (checkout, trials and the library work without one). It is a service like any other, so it needs `service` (`yard me --json` `.team_permissions`), and a plan that no longer includes services stops it with the rest. Docs: https://docs.yard.sh/v1/platform/storefront/landing-page.md (adding a page, layout, limits, video, removing it), https://docs.yard.sh/v1/platform/storefront/landing-page/integration.md (`window.yard`, every attribute and field, embedding, CSP), https://docs.yard.sh/v1/platform/storefront/custom-domain.md.

## Bundle

- The landing page is the `services` entry of `.yard/settings.json` whose `url` is `/` (project-files.md, services.md). A new project's draft starts with one: a static service named `landing-page` holding a starter `index.html` and `styles.css`. `yard init --page` adds a static one in a linked project, named `landing-page` (or the next free name) in `.yard/landing-page/` with starter files, and pushes it (works without a terminal); a project whose release already has a service at `/` gets that one's files instead. A release without a service at `/` has no landing page.
- Its files follow the service rules (services.md): the service extensions, nested folders, no dotfiles, `__yard/` reserved, the plan's `service_max_*` limits. `index.html` answers `/` and each folder with one; a static page answers other missing paths with its `404.html`, or a plain Not Found. Add an entry (`_service.ts` or `_service.js`) when the page needs server code: the same service runs it, and its files are still served directly. Video plays with seeking: H.264/AAC `.mp4`, `muted playsinline` to autoplay, `preload="metadata"` with a `poster`, captions as `.vtt`.
- Use relative URLs (`href="styles.css"`, `fetch("app/items")`): the page serves under `/<slug>/` and `/<slug>/@<sandbox>/`, so a root-absolute `/styles.css` 404s.
- A page that sends its own `Content-Security-Policy` must allow `script-src https://yard.sh`, `connect-src 'self'` and `style-src 'unsafe-inline'`, or `embed.js` and the hooks below break.

## Hooks

Yard injects `embed.js` at the start of the head of every HTML page the service at `/` serves; other services get none, except the project's sign-in page at the one address `auth.sign_in_path` names, while project accounts are on (yard-auth.md). `window.yard.project` is the public project JSON (https://docs.yard.sh/v1/api/public/get-public-project.md), synchronous, `null` when it could not load. An empty field is absent rather than `null` (check for the key), `tiers` arrive in the team's order with no field to sort them by, and the object reflects the saved release.

- `data-yard="<dotted path>"` sets `textContent` from `project` (`title`, `tiers.0.name`, `latest_release.tag_name`); add `data-yard-html` to write `innerHTML` (`latest_release.release_notes_html`). Copy such as a tagline, a description or an FAQ is the page's own text. After inserting DOM yourself, call `window.yard.refresh()`.
- `data-action="checkout"` with `data-tier-id` (the tier **key**; omit for the default tier), `data-interval` (`monthly` | `yearly`), `data-quantity` (seats on a `per_seat` tier, or 1-99 of a consumable), `data-gift`, `data-product="<key>"` (buy a product; the buyer must be signed in, and hold a required tier if it requires any) and `data-return-to` (with a product: a URL or a path relative to the page; bare means this page). `data-action="trial"` takes an optional `data-tier-id` of a trial-enabled tier. Clicks are handled and their default prevented; the attribute wins over `href`, so never reuse such an element as a plain link.
- `data-yard-when="signed_in|signed_out|owned|not_owned"` shows the element only in that state, by a rule page CSS cannot override; `embed.js` never touches the `hidden` attribute. On a first visit such elements stay hidden until the state resolves. The browser remembers the state for the page, so later visits start in it at first paint and switch if the fresh answer differs.
- `<html>` carries the same state for page CSS, set before paint: `data-yard-pending` (no answer yet), `data-yard-signed-in`, `data-yard-owned`. `html[data-yard-owned] .buy { display: none; }` shows Buy while Yard checks on a first visit and hides it for a known owner.
- JS: `window.yard.checkout({ tier?, interval?, quantity?, gift? } | { product, quantity?, interval?, returnTo?, for? })`, `trial({ tier? })`, `checkoutURL()`, `trialURL()`, `ownership()`, `purchase`, `refresh()`, `checkoutBase`, and for a project accounts sign-in page `signIn(email, { returnTo? })`, `linkSignIn()` and `signInWithYardURL({ returnTo? })` (yard-auth.md, Project accounts). Link parameters and the `return_to` rules: checkout.md. After a product checkout returns, `window.yard.purchase` is `{ product, status, purchase_id }` (taken off the URL) and `ownership()` already counts a `succeeded` purchase.

## Visitor state

`await window.yard.ownership()` is about this visitor's session with the project, the Yard Auth sign-in services see as `X-Yard-*` (yard-auth.md): `{ signed_in, user: { id, username, avatar_url } | null, owned, is_trial, is_subscription, trial_expires_at, trial_used, transaction_id, tier_key, tier_name, tier_id, tier_keys, products }`. `user.id` is the same per-project id the project's services get as `X-Yard-User-Id`. `trial_used` is true once the visitor has had the project's one free trial, running or ended: hide a trial button then. Match `tier_key` against `project.tiers[].key` (a holder from an older pricing revision has a `tier_id` the page no longer lists); `tier_keys` and `products` are the product holdings (products.md). It always waits for the live answer, never the remembered one, and returns `null` when Yard cannot answer (no reply within 8 s, or a page served without the project's data, such as the dashboard's preview): treat that as signed out.

A visitor is signed out until they sign in to the project: link to `__yard/auth/login?return=/` (and `__yard/auth/logout?return=/`), relative to the page. With project accounts on, the sign-in page, in this service or any other, signs people in by emailed link with `window.yard.signIn()` (without `returnTo` it sends the page's own `?return=`, where the gate puts the path the visitor was going to) and `window.yard.linkSignIn()`, and offers Sign in with yard with a link from `window.yard.signInWithYardURL()` (yard's sign-in at the project's root, back to the same `return`, or `null` where yard can't sign anyone in). `embed.js` takes the link off the address bar before the page's own scripts run, so read it with `linkSignIn()`, never from `location.hash`. Inside a frame the sign-in helpers do nothing. The whole page and every answer: https://docs.yard.sh/v1/platform/services/sign-in-page.md. The session covers the project on one host, so a custom domain and the `yard.sh` address each sign in separately. The page may also read the session itself with relative `fetch("__yard/auth/me")` and `__yard/products`, and deliver consumables with `POST __yard/fulfillments/{transaction_id}` (yard-auth.md, products.md).

## Testing

`yard dev` serves the page at `http://localhost:9875/<slug>/` with `embed.js`, live project data when logged in (otherwise a placeholder from settings.json with no `title` or releases, so those bindings keep the page's own text) and `ownership()` from the chosen persona (local-dev.md). Hosted, each sandbox serves the page at `/<slug>/@<name>/` with its own pricing; the try-then-ship recipe is in sandboxes.md.
