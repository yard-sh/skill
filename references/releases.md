# Releases and channels

A release is a project-wide snapshot: pricing, products, download buttons and download access rules, services (the landing page is the one at `/`), migrations and download files. Docs: https://docs.yard.sh/v1/platform/projects/releases.md (channels, promoting, archiving, rolling back, pinning, beta channels, files), https://docs.yard.sh/v1/platform/library/download-access.md (who may download each file), https://docs.yard.sh/v1/guides/releases/sync-github-releases.md (GitHub App and sync), https://docs.yard.sh/v1/platform/projects/storage.md (storage limit and each project's auto-archive).

## How releases serve

- Every release starts as a draft; a new project starts with one tagged `v1.0.0`, which holds that tag until it is published, retagged or deleted. `yard push` writes into it, and the plan caps open drafts (`403 draft_limit_reached`). Nothing serves a draft. Publishing stamps a tag (unique among non-archived releases, `409` on reuse) and puts the release in one channel; it stays editable, and an edit to a served release is live on save.
- The project and each sandbox follow one channel and serve its most recently published release. The project follows the protected, always-public `Production` channel; a new sandbox follows none. Precedence: pinned > rolled back > following. A rollback lasts until the next release lands in the channel; a pin lasts until `unpin` (sandboxes.md). So `yard releases publish <tag>` with the default channel is the go-live step.
- Other channels: `yard channels create <name>` (private and empty; `max_channels` per project with Production included, `403 channel_limit_reached`; Basic has Production only), `update <name> --name <new> | --visibility public|private` (a private channel is invisible to buyers' license keys and to `releases:read` keys), `delete <name> [--move-to <channel>] [--yes]` (moves its releases and followers; a run without `--yes` previews what changes), `list --json` (`channels[]` with `latest_version`, `sandboxes`, `project_follows`).
- Archiving takes a release out of its channel, frees its tag and deletes its download files; refused (`409`) while the project or a sandbox is pinned or rolled back to it. Unarchive returns it to the channel it left (or the one that channel's releases moved to), without its downloads. A project with auto-archive on (projects.md) archives its oldest published releases past its max after every publish; a release the project or a sandbox is pinned or rolled back to is out of the sweep's reach the same way, and a release marked exempt on its Release Settings page stays out of it while it still counts toward the max.
- Download buttons (`downloads.buttons` in settings.json, project-files.md): up to 10 rules `{ condition: contains|starts_with|ends_with|has_extension, value, label }` matched against the release's files: https://docs.yard.sh/v1/platform/library/download-buttons.md. A button whose file the user can't download shows disabled with what unlocks it. Files count toward the plan's storage (`413 storage_limit_reached` on publish).
- Download access (`downloads.access` in settings.json, project-files.md; the dashboard's Downloads page edits the same rules): up to 25 rules `{ condition: all|is|contains|starts_with|ends_with|has_extension, value, tiers: "any" | [tier keys], products: [product keys] }`, each naming `"any"`, tiers or products. Matching is plain text, ignoring case for A to Z only (any other letter must match exactly, so `É` is not `é`): no patterns, `all` takes no value, `is` is the whole filename, `has_extension` ignores a leading dot. A file no rule matches is public: anyone downloads it, signed in or not. Rules add up, so a file several rules match comes with anything any of them names; a rule can widen a file's audience but never narrow it, and keeping a file for one tier means no broader rule (such as the starting `all`) may match it. Holding counts for a tier when it is bought, claimed free, gifted or granted, an active subscription, or a running trial of that tier (a trial counts here, unlike for product requirements); `"any"` is any of those; a product counts while it is active and its requirement is met, one-time or subscription (a subscription product stops unlocking as soon as its required tier is gone, before it is set to end), never consumable. The team always downloads. A new project's draft and a blank release start with `{ "condition": "all", "tiers": "any", "products": [] }` (purchase-only, as before access rules), releases from before access rules were given the same rule, and a draft cut from a release copies its rules. A tier or product a rule names must be in the release and cannot be removed until the rule no longer names it. Public files are reached through a no-sign-in link (Copy Link on the Downloads page of a release the project offers), the Library (a signed-in non-buyer can open the project's library page when the served release has a public file), and `window.yard.project.public_downloads` on the landing page (https://docs.yard.sh/v1/api/public/get-public-project.md; empty in pre-order, when the Library lists no releases). The Library lists locked files with what unlocks them, and update checks with a license key list only the files the key's buyer may download (updates.md). Public downloads count in the download stats as downloads without a downloader.

## Commands

Writes target your open draft (or a new draft from the newest published release) unless `--release <tag|id>`; all take `--project`, `--dir` and `--json`. Each follower whose release changed is reported as `my-project: v1.4.0 -> v1.3.2`; in JSON every `deployed[]` entry names its target as `"project": "<slug>"` or `"sandbox": "<name>"`, and `serving[]` carries `{ from, to }`.

- `yard releases publish [tag] [--file <path>]... [--name] [--notes | --notes-file] [--channel <name>] [--spec <file|->]`: uploads the files into the draft (up to 5 GiB each), then publishes it. With `--spec` (`{ project?, tag_name, release_name?, release_notes?, channel?, files? }`) the tag argument and those flags are refused. Without a terminal, the tag and flags are the whole request. A partial upload still publishes without the failed files and exits non-zero; when every file fails nothing is published. `--json`: `{ release: { id, version }, deployed, files, uploaded, failed }`.
- `yard releases promote <tag|id> --to <channel>`: moves a published release into another channel (nothing is copied); followers of the new channel serve it only if it is the newest there.
- `yard releases archive <tag|id> [--yes]` (asks first, naming each download file it deletes), `unarchive <tag|id> [--to <channel>]`.
- `yard releases list [--channel <name> | --drafts | --archived] [--page] [--limit]` (`.items[]`), `show <tag|id>` (files with size and SHA-256).

## GitHub

- Install the Yard GitHub App once per team: https://dash.yard.sh/integrations, or interactive `yard init` offers it. `yard init --json` and a failing `yard github link` print a single-use install link that expires in 15 minutes: hand it to the user and rerun. A GitHub account or org connects to one team at a time.
- `yard github link [owner/repo] [--channel <name>] [--move]` (a repo links to one project at a time; `--move` takes it from the other project), `unlink`, `list --json` (`links[]`).
- Publishing a GitHub release creates a published Yard release in the sync channel (default `Production`, so it ships): tag, title, notes and assets. GitHub drafts and pre-releases do not sync, and a private project does not sync. A GitHub tag that a Yard draft holds (a new project's draft holds `v1.0.0`) fails the sync until the draft is retagged, published under another tag or deleted. Editing the GitHub release re-syncs it; deleting it archives the Yard release.
- With `.yard/settings.json` at the tag, each declared section syncs too: services (each with files; an older file's landing page counts as one), migrations, `pricing.tiers`, `products`, `downloads.buttons` and `downloads.access`, each matched exactly, even when empty (a migrations directory with no `.sql` files leaves the release none, and `"access": []` makes every file public); an absent section is left as it was, and a `downloads` block without `access` keeps the release's access rules. New settings files list every section, so delete one from the committed file to keep managing it in the dashboard. A repository that declares any service owns the whole set, so a service only the dashboard added goes at the next sync. A section that fails validation records a sync error and the release keeps what it had (an invalid `access` list keeps the whole `downloads` block; a valid one naming a tier or product the release lacks keeps only the old access rules; a tag dropping a tier or product the rules name falls back access, then products, then pricing). Tags are immutable, so a settings fix lands with the next tag (or the dashboard's Sync with GitHub).
- A synced release edited on Yard (dashboard, CLI, agent or API) is marked Diverged and skipped by later syncs, new assets included, with a warning in its Sync Logs; Sync with GitHub, in the dashboard's release editor, overwrites it from GitHub again.
