# Local development: yard dev

`yard dev` runs the project on the machine the way Yard hosts it: every service under its mount, the one at `/` as the landing page with `embed.js` and the project's data, the `X-Yard-*` headers from a chosen persona, secrets, rooms, and a local database with the migrations applied. Docs: https://docs.yard.sh/v1/platform/services/local-development.md (first run, personas, panel, differences, troubleshooting). Iterate here, then `yard push`; real commerce (a purchase, a trial, a license key) needs a sandbox.

```sh
yard dev                        # serves http://localhost:9875/<slug>/ ; walks up to .yard/settings.json
yard dev --as user:pro --json   # default persona; one JSON event per line for scripts and agents
```

Flags: `--port <n>` (9875), `--dir`, `--project`, `--as <persona>`, `--root` (serve at `/` like a custom domain), `--open`, `--secrets-file <path>`, `--reset-db`, `--reset-rooms`, `--allow-local-egress`, `--no-panel`, `--offline` (no Yard lookups), `--json`.

- Needs `.yard/settings.json` with a service (an older file is upgraded to version 10 first, project-files.md). Each run downloads the current local runtime (about 40 MiB, checksum-verified) into `~/.yard/runtime/`; Linux needs glibc 2.35+, macOS 13.5+. One `yard dev` per working copy (a second refuses, naming the pid); the port is bound first, so a busy port fails at once (`--port`).
- No login needed. Logged in, `window.yard.project` is the live project (pricing and products from the published release, or from settings.json until something is published: `snapshot_source` `remote_unpublished`); offline or logged out it is built from settings.json without `title`, releases or images. Nothing else leaves the machine except a persona's checkout and trial links and `GET /api/v1/*` on the local origin, which is proxied to Yard.
- `--json` events: `ready` (`slug`, `runtime_version`, `landing_page` (the URL of the service at `/`, empty without one), `services[]` with `url`, `access`, `database` and `rooms` (`[]` when none), `panel`, `persona`, `database`, `migrations_applied`, `migrations_pending`, `secrets_loaded`, `missing_secrets`, `snapshot_source`, `warnings`), then `restart`, `validation_error` (`errors[]`), `migrations`, `log` (`service`, `level`, `message`), `request`, `runtime_error`, `runtime_download`, `notice`, `sign_in_link` (`email`, `link`), `simulated_purchase` (`email`, `tier` or `product`, `trial`), `stopped`. A fatal refusal (lock, port, settings, runtime) prints `Error: ...` on stderr and exits 1 with no event: run it in the background and watch the exit as well as `ready`.

## Personas

There is no real Yard Auth locally: a persona decides the `X-Yard-*` headers, `__yard/auth/me`, `__yard/products` and `window.yard.ownership()`, or a sign-in page's emailed link does, printed instead of mailed (below).

| Persona | Entitlement | Tier |
| --- | --- | --- |
| `anonymous` | none (no headers) | |
| `signed-in` | `none` | |
| `trial` (when a tier offers one) | `trial` | the first tier with a trial |
| `user:<tier key>` (one per tier) | `active` | that tier |
| `buyer:<product key>` (one per product) | `active`, or `none` when the product requires no tier | the first tier it requires, if any; holds that product |
| `team` (a team member, with team access) | `team` | |

Each signed-in persona has a fixed made-up UUID `X-Yard-User-Id` (the same in every project and run, where hosted each project knows a person by its own id; read it from `__yard/auth/me` or `/__yard/dev/api/state`, never hard-code it) and an email like `user-pro@example.com`. Personas come from the project's tiers and products (the published release when logged in, else settings.json). Pick one with `--as`, with the cookie (`curl -H 'Cookie: yard_dev_identity=user:pro' http://localhost:9875/<slug>/api/notes`), with `POST /__yard/dev/api/persona {"persona":"team","default":true}`, or at the picker `/<slug>/__yard/auth/login` (`__yard/auth/logout` clears it). The `team` persona holds team access as hosted (yard-auth.md), kept in a second cookie, `yard_dev_team`: picking any other persona clears it and `logout` leaves it, so after `logout` `team` services still open and are told the visitor is the team member. `yard_dev_identity=team` alone holds team access too. A persona the project no longer has serves as `anonymous` with a warning. Gating, header stripping, `__yard/auth/guest` and the cross-origin rules behave as hosted (yard-auth.md).

A project accounts sign-in page works locally too: `yard dev` answers its two calls as hosted (yard-auth.md, Project accounts) but sends no mail. The link is printed in the terminal and listed on the panel's Sign-in links card; it goes to the page `auth.sign_in_path` names (without one the first call refuses with `sign_in_page_missing`). Following it signs the browser in as that address, a made-up user with no username whose id comes from the address, and leaves `yard_dev_team` alone, so a `team` persona keeps team access. Every address gets a link, the developer's own included, since nothing is looked up. A link works once for 15 minutes and another browser is asked to confirm, as hosted; with no switch, drafts or limits locally, the refusals those cause never come. With a page named, and the page under a public service, a signed-out persona at an `authenticated` or `users` service lands on it with `?return=` as hosted (no switch needed); otherwise, and at a `team` service, the gate shows the persona picker, which stays at `__yard/auth/login` and in the panel. The page gets `embed.js` at its address and its service answers `frame-ancestors 'self'`. `yard dev` (at start and on each settings change) and `yard service check` warn when the page is under a service that needs sign-in, since a push with those settings is refused. Docs: https://docs.yard.sh/v1/platform/services/local-development.md, section Signing in by emailed link.

Buy and trial links on the project's pages come to `yard dev` first. Signed in as an address by its link, the visitor gets a small simulated checkout naming the address and the tier or product; Complete purchase (Start trial for a trial) makes the address hold it until `yard dev` stops, as `__yard/auth/me`, `__yard/products`, `ownership()`, `X-Yard-Entitlement` and the gates then say (a one-time tier as a purchase, a subscription tier as a subscription, a trial link as a trial), and a product's `returnTo` gets `yard_product`, `yard_status` and `yard_purchase` as hosted. Nothing is charged and nothing reaches yard. It shows the refusal yard's checkout would give (a product needing a tier the address lacks, a link `for` someone else, a gift, which it doesn't simulate). A persona goes on to yard's checkout; a signed-out visitor goes to the sign-in page when it is in a public service, then back to checkout, else to yard's checkout. The panel's Simulated purchases card lists what each address holds and clears it. Docs: same page, section Buying as a test address.

## Database, secrets, rooms, panel

- `env.DB` is `.yard/dev/data.sqlite`; `.yard/migrations/*.sql` are applied in order and recorded as hosted (a failing file leaves its earlier statements applied: fix it to re-run from the top, or `--reset-db`). New files apply on save. `yard db query` still targets the hosted database; query the local one from the panel or with `POST /__yard/dev/api/db/query {"sql":"...","params":[]}`.
- Secrets: `.yard/dev/secrets.env` (`KEY=value`, the hosted grammar; never pushed). A startup warning names remote secrets with no local value.
- Rooms run with the hosted contract; storage under `.yard/dev/rooms/<service>/` survives restarts (`--reset-rooms` clears it; `--reset-db` leaves rooms alone). Live connections end on every restart, which is every save, so reconnect logic is exercised early.
- The control panel `http://localhost:9875/__yard/dev/` sits over loopback-only JSON endpoints under `/__yard/dev/api/`: `GET state` (URLs, services, personas, runtime, migrations, secret names), `GET requests?since=&limit=` and `requests/stream` (SSE), `GET logs?service=&since=` and `logs/stream`, `POST persona`, `POST db/query`, `POST migrations/apply`, `POST db/reset`, `POST rooms/reset`, `POST purchases/clear {"email":"..."}` (POSTs need `Content-Type: application/json`). `--no-panel` turns off only the page; these endpoints stay on. An automated check: start `yard dev --json`, wait for `ready`, curl the URLs with persona cookies, read `requests` and `logs`, stop the process.

## Differences from hosted

Every service directory, migrations, settings.json and the secrets file are watched; any save (assets included) re-validates with push's rules, restarts the runtime in under a second and reloads open landing page tabs. The 50 ms CPU budget is not enforced; egress to private networks is blocked unless `--allow-local-egress`; the Cache API is unavailable; `request.url` is `http://localhost:<port>/...`; there is no consent screen, sandbox, draft gating, sign-in mail (the link is printed) or `yard service logs` (use the panel). A persona's checkout and trial links go to Yard (test real buying in a sandbox), where a product checkout's `returnTo` to `http://localhost:<port>` is refused unless it is a Yard Auth redirect URI origin; a test address buys on the simulated checkout (above). Simulated purchases fire no webhooks, send no receipt and are never refunded, and there is no Delete or gift locally: try those in a sandbox.
